# License 诊断与恢复开销优化

日期：2026-09-30。用户授权实施性能评审中确认的小范围优化；本轮不改变授权范围、
5 秒回拨/300 秒前跳阈值、签名修复规则、节点额度和到期后降额续期语义。
产品改动限于五个 FE 类；BE、页面、网络协议和持久化外壳格式保持原样。
实现、构建及回归测试已完成；下列运行结果以本轮独立回执为准。

## 修改与边界

| 改动 | 实际行为 |
| --- | --- |
| `OriginStatement.getSafeSql()` | 非 null 原文按需计算安全文本，之后按实例复用（首次并发调用允许重复计算）；普通 SQL 复用原 String，不复制长串。缓存为 transient volatile，Gson 恢复后重新计算，输入中的伪造缓存字段不生效 |
| `StmtExecutor` 的 Profile 摘要 | 把原文交给原有 String builder 唯一脱敏，消除该调用链相邻的两次脱敏；其他直接传原文的调用方仍受 builder 保护 |
| `NereidsParser.getHintMap()` | 首次真正遇到 hint 时计算一次敏感性，供该次解析的所有 hint 共用；原来的 H 个 hint 对应 2H 次全文判定变为一次，无 hint 时仍为零次 |
| `LicensePersistRecord` / `LicenseManager` | 已成功应用状态最多保留三个可信槽；同一 verifier 对象、完整 compact 原文及原提交版本一致时复用验签结果，同一记录内的重复有效槽也去重 |

缓存不改变执行 SQL 或会话路由。PROCESSLIST 仍按完整 SQL 判断敏感性后截取展示，
不能先截前 100 字再判断。默认解析、路由和审计中的直接 String 扫描仍存在，
本轮不把“每条 SQL 的所有扫描降为一次”作为结果，也没有引入全局 SQL 缓存。

验签复用仅限最近一次成功应用状态，无历史链或全局缓存；冷启动的第一份记录必须验签。
verifier 的公钥集合在构造时复制且不可变，换 verifier 即使公钥内容相同也重新验签。
原文或原提交版本变化必须重新核验；坏槽不形成负缓存。每次仍重建许可状态并检查
部署、最高序号、槽顺序、回执与额度不变量；成员快照、时钟事实和版本继续正常应用。
应用中途失败不能把尚未成功应用的槽放入复用状态。

本轮没有把每秒成员检查改成纯事件驱动，也没有改为增量 journal；这两项会涉及更多恢复和通知路径。
仍会解析完整记录、检查结构并更新其他事实，减少验签不等于消除全部回放成本。

## 验证口径

新增回归使用原有测试类，覆盖：

- 缓存懒计算、重复显示、原 String 引用、null、两种 Gson 反射恢复及注入缓存字段；
- 无 hint 零额外判定、多 hint 普通/敏感 SQL 单次判定，非法敏感 hint 的异常与控制台保护；
- 冷恢复的不同证书首次验签、重复水位零额外验签、实例之间无共享缓存；
- 同 ID 原文篡改、同 ID 重新签名但回执冲突、原提交版本变化、未知公钥及换公钥；
- 回执/最高序号/许可版本/槽顺序损坏仍拒绝，成员数量和 CLOCK_SUSPECT 仍传播；
- 应用失败后重试必须重新核验尚未成功应用的证书。

本轮 JDK 17.0.4 离线 Maven 构建实际执行 31 个授权测试类，**287 项通过，零失败、错误或跳过**。
其中 SQL 脱敏 6 项、SQL 解析 9 项、Manager 38 项；共新增 8 个测试方法。
FE package、Checkstyle、源码许可头及空白检查通过。构建前后绑定的 6,986 个输入文件无变化。
本轮未改发行器，不把上轮 Python 测试重算成本轮新增验证。

## 实际性能对照

本轮对照 A 是优化前的 **授权版** `4ba3b488ddc` 自用包，B 是本轮优化候选。
这不是最初 P4 的无授权版本对照，不能用它追认原 P4 已经通过性能等效验收。
实际使用新建的单 FE/BE、同一百万行数据和有效证书执行 A–B–B–A；每块重启 FE/BE，
metadata、cache 各使用相同的 60 秒预热和 30 秒计时，并保留每次完整结果核对、CPU 边界和延迟样本。
这一短测用于发现本轮修改导致的明显回退，不证明 1%/2% 精度、最大容量或长期稳定性。
计时窗默认关闭 Profile，也不据此声称测得 Profile 开启场景的收益。

最终 `quick-abba-v3` 真实退出码 0，四块八窗全部结束，**36,720 次计时请求全部正确**，
零错误、零丢失；每次查询均核对结果向量，CPU 计时边界和成对到达计划摘要核对通过。
setup 与四块测试共十个服务进程组全部停止，没有强杀；没有修改主机时钟、swap、sysctl 或其他安装。

## 时钟运维说明

本轮保留现有时钟规则。主 FE 已提交的 CLOCK_SUSPECT 会传播，重启不会清除；
需要签名修复票据并满足修复挑战和本机时间窗口。仅从 FE 的本地异常不会自动反向传播，
校正后重启能否恢复取决于其墙钟与持久高水位是否匹配。
主 FE 水位领先从 FE 本机墙钟超过 5 秒，也可能使该从 FE 本地进入可疑状态。
阈值比较的是与可信时间/单调推进锚点的偏差，不能仅按某一次 NTP 调整量判断。
运维应先校准各节点时间再启动集群，并提前准备离线时钟修复能力。

后台提交异常仍可能使许可变为 NOT_READY；本次优化不会把持久化不确定状态当作可放行业务读取的状态。
原始 P4 的 CPU、尾延迟变化、启动状态差异以及尚不足以判定原因的结论继续保留。
