## BUG-001：JDBC 字符串数组不能原样往返

**位置**：

- `be/src/vec/data_types/serde/data_type_string_serde.cpp:423–434`
- `fe/be-java-extensions/jdbc-scanner/src/main/java/org/apache/doris/jdbc/MySQLJdbcExecutor.java:303`

**触发条件与影响**：通过 JDBC catalog 读取 Doris/MassDB 的 `ARRAY<STRING>` 等字符串数组，
元素包含反斜杠或双引号。远端数组文本不是可靠的 JSON，但读取端按 JSON 解码：例如原本的
反斜杠和字母 `n` 会被转换为换行；双引号可以使整次读取失败。若错误解码后用于
`INSERT ... SELECT`，目标值可能与源值不同；本轮未执行该写入场景。

**证据**：以下只读 SQL 已实际执行；使用 `CHAR()` 消除 SQL 字面量本身的转义歧义。

```sql
SELECT ARRAY(
    CONCAT('a', CHAR(92), 'n'),
    CONCAT('a', CHAR(34), 'b'),
    'abc'
);
```

MySQL 协议的结果文本为：

```text
["a\n", "a"b", "abc"]
```

其中第一项在协议文本内是字节 `61 5c 6e`，不是换行。离线重新编译当前仓库的
`MySQLJdbcExecutor.java`，分别把上述三项的数组表示传给其真实 `convertArray` 方法：

| 输入文本 | 期望元素 UTF-8 十六进制 | 实际结果 |
| --- | --- | --- |
| `["a\n"]` | `615c6e` | `610a`，反斜杠和 `n` 被改成换行 |
| `["a"b"]` | `612262` | `JsonSyntaxException: Unterminated array` |
| `["abc"]` | `616263` | `616263`，对照组正常 |

**根因**：字符串 SerDe 在嵌套层只添加两侧双引号，直接写入原始字符串；JDBC executor
使用 `gson.fromJson()`，两端对引号、反斜杠的编码约定不一致。近期数字精度、NULL 元素修复
没有覆盖这个问题。

**建议修复与回归**：为复杂类型的跨 JDBC 传输确定可逆的编码约定，配套修改输出与解析，
同时评估现有客户端的文本格式兼容性。覆盖反斜杠、双引号、控制字符、Unicode、NULL、
空字符串及嵌套数组；比较源表、JDBC 查询和写回后的元素字节。

**验证边界**：已验证实时 SQL 序列化和当前 Java 生产方法解码，没有运行完整的 JDBC catalog
扫描和写回。当前机器的取证文件：
`/tmp/massdb-jdbc-audit-20260907/{observed-live-query.txt,array-decode-result.txt,ArrayDecode.java,run-offline.py}`。
可用 `python3 /tmp/massdb-jdbc-audit-20260907/run-offline.py` 重跑离线验证；`/tmp` 文件不是持久化交付物，
关键输入、输出与根因已记录在本文。

## BUG-002：字段通配符错误匹配 NULL

**位置**：

- `be/src/vec/functions/function_search.cpp:1027–1034`
- `be/src/olap/rowset/segment_v2/inverted_index/query_v2/all_query/all_query.h:97–101`
- `be/src/olap/rowset/segment_v2/inverted_index/query_v2/weight.h:107–119`

**触发条件与影响**：V2 倒排索引、字段存在 NULL，执行 `search('a:*')`。
代码明确将此语法定义为匹配字段非 NULL 值，实测却返回 NULL 行，导致存在性过滤和计数错误。

**已执行的最小复现**（数据库名应选用新的测试名称）：

```sql
CREATE DATABASE audit_search_20260907_01;
CREATE TABLE audit_search_20260907_01.t (
    id INT,
    a STRING,
    b STRING,
    INDEX ia(a) USING INVERTED,
    INDEX ib(b) USING INVERTED
)
DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES("replication_num"="1", "inverted_index_storage_format"="V2");

INSERT INTO audit_search_20260907_01.t VALUES
    (1,NULL,'yes'), (2,'yes',NULL), (3,'no','no'),
    (4,NULL,NULL), (5,'yes','yes');

SET enable_common_expr_pushdown=true;
SET enable_inverted_index_query_cache=false;

SELECT id FROM audit_search_20260907_01.t
WHERE search('a:*') ORDER BY id;
-- 实际：1,2,3,4,5

SELECT id FROM audit_search_20260907_01.t
WHERE a IS NOT NULL ORDER BY id;
-- 期望及对照：2,3,5
```

**根因**：构造 `AllQuery` 时传入存储字段名；`AllWeight` 未使用传入的字段 binding key，
解析 NULL 位图时退回存储字段名。V2 使用字段 unique ID，而 NULL resolver 以 SQL 逻辑字段名
查找迭代器，导致无法取得该列 NULL 位图。映射两端分别见
`be/src/olap/rowset/segment_v2/segment_iterator.cpp:347–355` 和
`be/src/vec/functions/function_search.h:105–107`。

额外实测显式指定 `search('a:*', '{"mode":"standard"}')` 仍返回全部 5 行。
切换查询模式不能解决本项问题。

**建议修复与回归**：使 `AllWeight` 保留并使用字段绑定；增加 V2 的普通列、别名、组合条件和
NULL/非 NULL 混合输入测试。多段索引还需单独检查位图行号范围。

## BUG-003：默认 Lucene 模式的复合 SEARCH 被 SQL NOT 取反时多返回 NULL 行

**位置**：

- `be/src/olap/rowset/segment_v2/inverted_index/query_v2/boolean_query/occur_boolean_weight.cpp:143–151`
- `be/src/olap/rowset/segment_v2/inverted_index/query_v2/intersection.h:33–62`
- `be/src/olap/rowset/segment_v2/inverted_index/query_v2/scorer.h:53–57`
- `be/src/vec/functions/function_search.cpp:521–541`

**触发条件与影响**：使用默认的 `lucene` 模式，对含多个可空字段的 AND/OR 搜索结果应用外层 SQL `NOT`。
应为 UNKNOWN 的行被当作 FALSE，再被 NOT 变成 TRUE，造成静默多返回数据。

**已执行复现**：使用 BUG-002 的表和会话设置，在清理前执行：

```sql
SELECT id FROM audit_search_20260907_01.t
WHERE NOT search('a:yes AND b:yes') ORDER BY id;
-- 实际：1,2,3,4

SELECT id FROM audit_search_20260907_01.t
WHERE NOT(a = 'yes' AND b = 'yes') ORDER BY id;
-- 期望及对照：3
```

此表的索引不分词，`yes` 是完整值。第 1、2 行是 `NULL AND TRUE`，第 4 行是
`NULL AND NULL`，均应为 UNKNOWN；对 UNKNOWN 取 NOT 仍为 UNKNOWN，不能通过 WHERE。
第 3 行为 `FALSE AND FALSE`，取反才应返回。

**已排除的干扰**：复现时关闭了倒排查询缓存。以下对照均返回正确结果：

- `NOT search('a:missing')` 返回 `2,3,5`。
- `NOT search('a:yes')` 返回 `3`。
- `search('a:yes OR b:yes')` 返回 `1,2,5`。
- `search('a:yes AND NOT b:missing')` 返回 `5`。

**模式和 OR 对照**：又创建了相同数据的独立测试表，实际执行以下查询：

| WHERE 条件 | 实际返回 id | 正确 id |
| --- | --- | --- |
| `NOT search('a:yes AND b:yes', '{"mode":"lucene"}')` | `1,2,3,4` | `3` |
| `NOT search('a:yes AND b:yes', '{"mode":"standard"}')` | `3` | `3` |
| `NOT search('a:yes OR b:yes')` | `3,4` | `3` |
| `NOT(a = 'yes' OR b = 'yes')` | `3` | `3` |
| `NOT search('a:yes OR b:yes', '{"mode":"standard"}')` | `3` | `3` |

**根因**：`SearchDslParser.java:1717` 默认选择 `lucene` 模式（文件位于
`fe/fe-core/src/main/java/org/apache/doris/nereids/trees/expressions/functions/scalar/`）。
`function_search.cpp:693–720` 为该路径构造 `OCCUR_BOOLEAN`；
`OccurBooleanWeight::effective_must_scorer()` 使用 `make_intersect_scorers()` 合并 MUST 子项。
后者在 `intersection.cpp:65–91` 构造的 `Intersection` 没有实现 NULL 位图接口，继承
`Scorer` 的 `false/nullptr` 默认实现。因此最终抽取 NULL 集合时得到空集合。
OR 使用的 `BufferedUnion` 同样没有保留这个接口的语义。

**建议修复与回归**：布尔 scorer 需要同时保留 TRUE 和 UNKNOWN 的正确集合，按三值逻辑组合，
不能只交并 TRUE 集合。覆盖默认/显式 Lucene 模式的 AND、OR、外层 NOT、全无交集、嵌套和多字段 NULL。
本次 `standard` 对照在该单段数据上正确，不等同于证明它在所有查询和历史多段索引上均正确。

## BUG-004：SEARCH 缓存的 TRUE/NULL 两部分可被分别读到

**位置**：

- `be/src/vec/functions/function_search.cpp:371–389`：缓存读取与 NULL 未命中分支。
- `be/src/vec/functions/function_search.cpp:549–557`：TRUE、NULL 两次独立插入。
- `be/src/olap/rowset/segment_v2/inverted_index_cache.cpp:117–141`：独立的键级 lookup/insert。
- `be/src/olap/rowset/segment_v2/inverted_index_cache.h:195–207`：两个不同键的编码。

**触发条件与影响**：开启倒排查询缓存，搜索字段含 NULL。同一数据段、同一 DSL 的并发查询
可能在首次填充缓存期间只读到 TRUE 位图；缓存单独淘汰 NULL 项也能形成此状态。
该路径把“NULL 缓存不存在”当成“结果没有 NULL”，对外层 `NOT` 等逻辑返回错误数据。
这与 BUG-003 独立，单字段查询也受影响。

**代码可达的操作交错**（静态分析，未执行线程调度复现）：

1. 同一 DSL 的 TRUE 与 NULL 键初始均不存在；线程 A 完成正确计算。
2. A 在 `function_search.cpp:551` 插入 TRUE 位图后暂停，还未执行第 557 行。
3. 线程 B 查同一数据段和 DSL，在第 371 行命中 TRUE 键，在第 381 行找不到 NULL 键。
4. B 在第 384–389 行新建空 NULL 位图并直接返回。
5. A 才在第 557 行插入 NULL 位图；不能纠正 B 已取得的结果。

这两次插入没有包在共同的锁或原子缓存项中，底层缓存接口也不提供成对读写。
即使不考虑淘汰，上述首次填充交错已经足以构成错误。

以 BUG-002 的数据和单字段 `search('a:yes')` 为例，TRUE id 集合为 `{2,5}`，NULL 集合为
`{1,4}`；正常 `NOT search('a:yes')` 只返回 `{3}`。若丢掉 NULL 集合，取反将得到 `{1,3,4}`。
这里的错误集合是依据代码计算所得，不声称本轮已在线捕获该并发结果。

**建议修复与回归**：把 TRUE/NULL 一起放入一个缓存项，使发布、命中和淘汰保持一致。
最低限度应在任一键未命中时重新计算，不可把 NULL 未命中替换为空集合。
增加可控调度的缓存填充测试及单独淘汰 NULL 项的测试，比较缓存开启与关闭时的结果。

## BUG-005：事务发布覆盖其他事务的 BE 可见版本通知

**位置**：

- `fe/fe-core/src/main/java/org/apache/doris/transaction/PublishVersionDaemon.java:68–70,266–277`
- 同文件第 306–321 行的 `addBackendVisibleVersions()`，第 371–397 行的批量发送。
- `fe/fe-core/src/main/java/org/apache/doris/transaction/DatabaseTransactionMgr.java:1182,2356–2357`

**触发条件**：在两次 `sendBackendVisibleVersion()` 之间，尝试完成多个事务。
默认开启并行发布时也会发生；切为串行无法消除累计值被覆盖的问题。

**根因**：第 272–273 行没有声明局部变量，赋值对象是实例字段
`partitionVisibleVersions`、`backendPartitions`。每次处理事务都会把等待发送的累计 map
替换为空 map；后续 `finishTransaction()` 填入本事务结果，再将实例 map 与自身合并。

串行情况下，T1 产生的分区通知在 T2 进入时被清空，只留下最后一次尝试完成事务产生的通知。
如果 T2 因条件未满足而提前返回，甚至可能留下空 map。并行情况下，A 把 map A 传入
`finishTransaction()` 后，B 替换实例字段为 map B；A 返回后第 277 行重新读取的却是 map B，
导致 A 的结果无法正确合并。字段赋值及结果填充未遵守发送/合并端的 `visibleVersionsLock` 协议。

**实际复现**：在独立 JVM 编译当前仓库的 `PublishVersionDaemon.java`，通过反射连续调用真实
`tryFinishTxnSync()`。仅将事务管理器替换为本地 Java proxy：回调填入分区版本和 BE 映射、
把事务标为 VISIBLE。没有启动 FE、访问数据库或发送 RPC。

```text
after txn 101: versions={101=7}, backends={1101=[101]}
after txn 202: versions={202=7}, backends={1202=[202]}
expected partitions=[101, 202]; actual=[202]
```

验证的是生产方法的累计状态错误，不是完整事务流程或集群并发实测。
源码和结果：`/tmp/massdb-publish-audit-20260907/{PublishAccumulatorCheck.java,result.txt}`，
并归档到 `.build-records/performance-audit-20260907.tar.gz`。

**影响与边界**：FE 已独立完成事务 VISIBLE 和分区版本更新。
丢失的是 `UpdateVisibleVersionTask`：BE 经
`be/src/agent/task_worker_pool.cpp:2304–2307` 更新用于 compaction 的 `VersionWithTime`
（`be/src/olap/olap_common.h:583–596`）。
`be/src/olap/tablet.cpp:1227–1267` 用它筛选 compaction rowset，滞后可能推迟部分合并，
增加 rowset 保留和潜在读放大；可见版本数量的报告也可能偏低。
代码有数量/时间阈值兜底，不能声称所有 compaction 都停止，更不能据此声称永久数据丢失。

**已有补偿**：BE 后续 tablet report 上报分区版本，FE 的 `PartitionInfoCollector` 收集当前版本，
`TabletInvertedIndex.java:486–495` 找出落后分区，`ReportHandler.java:1312–1317` 补发通知。
延迟取决于采集、上报和任务队列，不能保证固定 60 秒内恢复。

**修复建议**：每事务创建局部 map，向 `finishTransaction()` 和合并函数传递同一对局部引用；
实例 map 只在锁内累计、发送和清空。不要为修复此问题把整个事务完成流程包进全局锁。

**应补回归**：两个不同分区串行完成、第二事务未完成、两个数据库并行完成、发送与合并交错；
断言全部应发的分区/BE 映射仍保留，并验证 BE 可见版本最终单调更新。
